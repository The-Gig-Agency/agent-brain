# echelon — v0.2 Debugging Core

## Purpose

v0.1 proved a narrow thing:

- retry suppression plus adaptive search policy can beat weak debugging baselines

v0.2 exists to test the next harder claim:

- can routed policy beat `fixed_heuristic` on the same debugging-core wedge?

Do not widen scope for v0.2.

## Non-goal

v0.2 is not for:

- more domains
- more regimes
- broader orchestration
- more agent abstractions
- more ontology

The only goal is to beat the best current simple heuristic on the existing wedge.

## Current gap

Right now:

- routed policy beats `naive_retry`
- routed policy beats `always_compound`
- routed policy ties `fixed_heuristic`

That means Echelon is showing value, but not yet a differentiated win over the strongest simple debugging heuristic in the current suite.

## Hypothesis

The current `fixed_heuristic` remains competitive because the synthetic worlds still reward a clean inspect-then-fix flow that does not require much adaptive control.

So v0.2 should not start by adding more logic everywhere.
It should make the wedge more diagnostic:

- cases where static inspect order is suboptimal
- cases where stale priors should be abandoned
- cases where delayed transition costs matter
- cases where drift and misleading evidence punish rigid heuristics

## v0.2 Goal

Pass if:

- routed policy beats `fixed_heuristic` on cost-adjusted success in debugging-core

And ideally also:

- lower dead-end persistence
- equal or lower hysteresis
- better transition timing on ambiguous cases

## Minimal Build Plan

### 1. Strengthen the case set

Add a small number of harder debugging-core cases that specifically stress:

- misleading early evidence
- false-positive inspection paths
- delayed but decisive signals
- local minima that require switching away from a plausible path
- cases where static inspect order wastes budget

Target:

- 3 to 5 additional cases max

### 2. Improve transition policy, not ontology

Keep the same narrow regime set.

Tune:

- explore -> prune timing
- prune -> compound timing
- drift detection under contradictory evidence
- failed-path suppression when a path looked promising but turns bad

Do not add new regime labels just to explain misses.

### 3. Add `fixed_heuristic`-specific diagnostics

Per case, compare routed policy against `fixed_heuristic` on:

- first three actions
- transition timing
- cost before first high-quality signal
- dead-end persistence

This should make it obvious why routed policy wins or loses.

### 4. Tighten the go/no-go metric

v0.2 should be judged primarily on:

- cost-adjusted success vs `fixed_heuristic`

Secondary:

- repeated failed-path reduction
- dead-end persistence
- hysteresis control

## Suggested Success Criteria

v0.2 is promising if:

- routed policy beats `fixed_heuristic` on the focused suite overall
- the win is not driven by one pathological case only
- hysteresis stays low
- improvements can be explained by better search adaptation, not benchmark quirks

## Suggested Failure Criteria

v0.2 fails if:

- routed still only ties `fixed_heuristic`
- the only way to win is adding benchmark-specific hacks
- hysteresis rises sharply
- transition logic becomes too brittle or opaque

## Implementation Priorities

1. Add harder debugging-core cases
2. Add diagnostics comparing routed vs `fixed_heuristic`
3. Tune transition logic on those cases
4. Re-run the focused suite
5. Write findings before widening scope

## Decision Rule

If v0.2 cannot beat `fixed_heuristic` on the narrow wedge, do not expand the product surface.

Either:

- improve the control logic further

or:

- accept that the real moat may be narrower than hoped

That is the right scientific posture for this stage.
